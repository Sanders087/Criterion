# Criterion: запуск в Docker и Amvera

Ветка `docker` содержит полный сайт Criterion 1.15 и модуль ПДн в **одном контейнере**: Next.js на Node.js 24, SQLite и Python 3.12 с Natasha/Presidio. Workers, D1 и Sites для запуска не нужны. Наружу открыт порт `3000`; распознавание ПДн работает внутри контейнера на `127.0.0.1:8100`.

## Запуск в Amvera

1. В существующем приложении выбрать окружение **Docker**, одну реплику и постоянное хранилище. В корне ветки уже есть `Dockerfile` и `amvera.yml`: порт приложения `3000`, внешний порт `80`, хранилище `/data`. Команду запуска вручную не задавать. Для первого теста выделить 1.5–2 ГБ RAM, затем подобрать ресурсы по метрикам своей нагрузки.
2. В «Переменные» добавить значения на этапе **Запуск**:

   | Переменная | Значение |
   |---|---|
   | `AUTH_PUBLIC_URL` | HTTPS-адрес приложения, например `https://criterion-matveygu.msk1.amvera.tech` |
   | `PII_ANALYZER_TOKEN` | Отдельный случайный секрет: 32–256 ASCII-символов без пробелов |
   | `OPENAI_API_KEY` | Ключ модели с доступом и доступным балансом |
   | `OPENAI_MODEL` | Необязательно; по умолчанию `gpt-4.1` |

   Секрет можно создать локально: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Скопировать его в Amvera; в Git не добавлять. `PORT=3000`, путь базы и `PII_ANALYZER_URL` уже задаёт контейнер. Установленный ранее `PORT=3000` можно оставить.
3. Из папки репозитория выполнить:

   ```sh
   git switch docker
   git remote -v
   ```

   Если remote `amvera` уже есть, повторно добавлять его не нужно. Иначе взять адрес из приложения Amvera и выполнить `git remote add amvera <адрес>`. Загрузить ветку:

   ```sh
   git push amvera docker:master
   ```

   Amvera использует ветку `master` своего репозитория. Прямая отправка `docker:master` подходит, пока в Amvera нет отдельных коммитов. При ошибке `fetch first` сначала выполнить `git fetch amvera master` и изучить `git log --name-status docker..amvera/master`; не использовать force push.

   Если нужно сохранить отдельную историю Amvera, использовать локальную ветку `amvera-deploy`. Создать её один раз командой `git branch amvera-deploy docker`. После проверки удалённых изменений отправлять обновления так:

   ```sh
   git fetch amvera master
   git switch amvera-deploy
   git merge --no-edit amvera/master
   git merge --no-edit docker
   git push amvera HEAD:master
   git switch docker
   ```

   При конфликте остановиться и разрешить его перед следующей командой. В GitHub отправлять только `docker`; `amvera-deploy` используется для Amvera. Это особенно важно, если в истории хостинга есть удалённые `.env`: слияние этой истории в `docker` перенесёт старые секреты на GitHub. Удаление файла не удаляет его старые версии; попавшие в Git секреты следует заменить.

   При запросе авторизации вводить данные Amvera в Git, не в чат. Альтернатива — GitHub-интеграция с веткой `docker`, если есть права настроить webhook репозитория.
4. Дождаться успешной **сборки и запуска**. В логах должны появиться готовность Python, `Criterion: database migrations ready.` и готовность Next.js. Если приложение было создано с другой конфигурацией, сверить порты и `/data` в настройках Amvera. После изменения переменных выполнить перезапуск.
5. В настройках Kubernetes-проб вставить [deploy/amvera/probes.yml](deploy/amvera/probes.yml). Этот отдельный файл не применяется автоматически из Git. Startup/readiness проверяют сайт, базу и Python; liveness проверяет порт. Проверка готовности не проверяет оплату, доставку почты или доступность модели.
6. Открыть `/api/health`: ожидается `{"status":"ready"}`. На сайте зарегистрироваться, сохранить код восстановления, создать договор и проверить сохранение после перезагрузки страницы. Пример для чата: [вымышленный договор услуг](tests/fixtures/pii-services-contract.txt). После перезапуска приложения аккаунт и документ должны остаться.

Для полноценного ИИ нужен работающий ключ и доступ сервера к API. Без ключа сайт запускается, но ИИ недоступен. При недоступном Python запрос к модели блокируется.

## Почта и оплата

Для писем отдельно задать `RESEND_API_KEY` и `EMAIL_FROM` с подтверждённым отправителем; `EMAIL_REPLY_TO` необязателен. Без них вход и регистрация работают, восстановление доступно по сохранённому резервному коду. Доставку письма проверить на реальном адресе после настройки.

Оплата из 1.15 сохранена: готовый договор и экспорт открываются после оплаты, кроме прежних документов с доступом `legacy`. В новой среде оплата по умолчанию отключена. Её включает команда с корректными настройками `TBANK_*` из [.env.example](.env.example). Публичный URL магазина и уведомлений должны вести на **новый домен**. Прежний VPS-шлюз привязан к старому Sites; его нельзя включать без отдельного переноса конфигурации. При прямом подключении оставить `TBANK_GATEWAY_URL`, `TBANK_GATEWAY_SECRET` и `TBANK_NOTIFICATION_URL` пустыми: URL уведомления формируется из нового `TBANK_PUBLIC_URL`. Проверить тестовый платёж до включения боевого терминала. Настройки чеков согласует владелец сервиса.

Если Amvera не принимает `TBANK_PASSWORD` из-за `!` или других спецсимволов, использовать **секрет** `TBANK_PASSWORD_BASE64`. Кодировать только исходный пароль (без внешних кавычек формата `.env`) в Base64 из UTF-8. Приложение восстановит его перед подписанием запросов и проверкой уведомлений банка. Одновременно задавать оба непустых значения нельзя; удалить `TBANK_PASSWORD` при переходе на Base64.

В PowerShell выполнить блок ниже и в скрытом запросе вставить исходный пароль. Результат попадёт в буфер обмена без вывода пароля или Base64 в консоль и без записи значения в историю команд:

```powershell
$tbankSecret = Read-Host 'TBANK_PASSWORD (исходное значение)' -AsSecureString
$tbankPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($tbankSecret)
try {
    $tbankPlain = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($tbankPointer)
    [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($tbankPlain)) | Set-Clipboard
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($tbankPointer)
    $tbankSecret.Dispose()
    Remove-Variable tbankSecret, tbankPointer, tbankPlain -ErrorAction SilentlyContinue
}
```

В Amvera: «Переменные» → добавить **секрет** `TBANK_PASSWORD_BASE64` на этапе запуска → вставить из буфера без кавычек → удалить прежний `TBANK_PASSWORD` → перезапустить приложение. Нужна версия кода с поддержкой этой настройки; одного переименования переменной в старой сборке недостаточно. Base64 обратим и тоже является секретом; после вставки очистить буфер командой `Set-Clipboard -Value ''`. Файлы `.env` и `*.env` остаются только локально.

Проверки Origin используют `AUTH_PUBLIC_URL`, поэтому за HTTPS-прокси не требуется подмена Host. Заголовки прежнего входа Sites не дают доступ к аккаунту. `TRUSTED_CLIENT_IP_HEADER` по умолчанию не задан: лимиты адреса/IP используют общий запасной ключ, лимиты email и токенов действуют отдельно. Указывать заголовок можно только после проверки, что прокси его **перезаписывает**, а клиент не может подделать. На публичном запуске настроить это совместно с администратором хостинга.

## Диагностика в логах

В Amvera откройте **«Лог приложения» → «Загрузить историю»**. Каждое диагностическое событие занимает одну JSON-строку. Поле `message` содержит поисковую метку `Criterion diagnostics v2:`. Для поиска по обращению пользователя используйте `requestId` из заголовка `X-Request-ID`. Формат событий, примеры поиска и ограничения описаны в [руководстве по диагностике](docs/diagnostics.md).

| Событие | Что проверено |
|---|---|
| `storage.entrypoint` | Наличие базы, владелец и права до и после существующей подготовки `/data` |
| `storage.snapshot`, `phase: "before_open"` | Путь из настройки, наличие файла до открытия, доступ текущего процесса, метаданные WAL/SHM и монтирование |
| `database.ready` | **Фактический `databasePath` открытого соединения SQLite**, успешность запроса (`queryOk`), миграций и режим журнала |
| `storage.snapshot`, `phase: "after_open"` | Состояние файла после открытия |
| `service.ready` | Python-модуль ПДн ответил на проверку готовности |
| `services.health` | Результаты HTTP-проверок ПДн и сайта; штатный `/api/health` сайта также выполняет запрос к БД |
| `integrations.configuration` | Только наличие настроек модели, почты и банка. Доступность провайдеров **не проверена** (`not_checked`) |
| `startup.failed`, `entrypoint.failed`, `service.failed`, `service.exited` | Этап ошибки, безопасный код или причина остановки без исходного текста исключения |

Для поиска базы смотреть `database.ready.databasePath`. `existedBeforeOpen: false` означает, что файла не было до открытия: это может быть новый пустой экземпляр, а не прежняя база. `processCanRead`/`processCanWrite` относятся только к пользователю процесса приложения, не к файловому сервису Data.

В Linux `mount.mountPoint` берётся из `/proc/self/mountinfo`. `separateMount: true` показывает отдельное монтирование, но **не доказывает сохранность тома между деплоями**; поэтому `persistenceVerified` остаётся `false`. `mountPoint: "/"` и `separateMount: false` означают, что отдельное монтирование для пути базы не найдено. `unknown` означает отсутствие достоверных данных, а `not_linux` ожидаем при запуске непосредственно в Windows.

Проверка сервисов выполняется каждые 30 секунд после готовности сайта; во время ожидания сайта — каждые 2 секунды. В лог попадают смены состояния и повторный статус раз в 5 минут. Тексты договоров, содержимое БД, пароли и ключи эти события не выводят. Диагностика не меняет права, пути или правила удаления данных; публичный `/api/health` по-прежнему не раскрывает метаданные хранилища.

Если есть доступ к shell **уже работающего контейнера**, можно выполнить:

```sh
node scripts/storage-diagnostics.mjs
node scripts/run-with-pii.mjs --diagnostics
```

Первая команда открывает только существующую базу в режиме чтения, не создаёт отсутствующую базу и не запускает миграции. Вторая также проверяет сайт и ПДн; код выхода `0` означает успешные проверки. Для локального Docker: `docker exec --user 10001:10001 criterion node scripts/run-with-pii.mjs --diagnostics`.

Если место хранения действующей базы неизвестно и копии нет, новый деплой может потерять данные, оставшиеся во временной файловой системе прежнего контейнера. Сначала получить подтверждение постоянного тома или копию через администратора платформы. Логи новой сборки показывают её собственный файл и не восстанавливают файл прежнего контейнера.

## Данные и обновления

База создаётся автоматически в `/data/criterion.sqlite`; миграции применяются при запуске с проверкой контрольных сумм. Каталог `/data` должен оставаться постоянным. Использовать **одну реплику**, не масштабировать эту сборку на несколько независимых SQLite. Не хранить базу в папке исходников.

Это новая база: аккаунты, документы и платежи из Sites/D1 **не импортируются автоматически**. Перед заменой старого production требуется отдельный проверенный экспорт/импорт с сохранением ID и сверкой платежей. Не загружать произвольный D1-файл поверх новой базы: неучтённая схема будет отклонена при старте.

Перед обновлениями делать резервную копию. `python scripts/backup-db.py` внутри контейнера создаёт согласованную копию в `/data/backups/`, включая данные WAL. Скачивать готовую копию в отдельное хранилище; копия на том же диске не защищает от потери диска. При ручном копировании исходной базы остановить приложение и сохранить базу вместе с `-wal`/`-shm`, если они есть. Для обновления повторить push; не удалять постоянное хранилище. Откат кода после изменения схемы требует проверки совместимости или восстановления резервной копии.

## Локальный Docker

Установить Docker, скопировать `.env.example` в `.env`, заполнить `PII_ANALYZER_TOKEN`; для ИИ также `OPENAI_API_KEY`. `AUTH_PUBLIC_URL=http://localhost:3000` оставить для локального запуска.

```sh
docker build -t criterion:docker .
docker volume create criterion-data
docker run -d --name criterion --env-file .env -p 127.0.0.1:3000:3000 --mount source=criterion-data,target=/data criterion:docker
docker logs -f criterion
```

Открыть `http://localhost:3000`. Для проверки обоих процессов:

```sh
docker exec criterion node scripts/run-with-pii.mjs --healthcheck
docker exec criterion python scripts/check-pii-endpoint.py --url http://127.0.0.1:8100/analyze
docker exec --user 10001:10001 criterion python scripts/backup-db.py
```

Остановка: `docker stop criterion`. Повторный запуск: `docker start criterion`. Том `criterion-data` сохраняет данные. Контейнер подготавливает права `/data`, затем сайт и Python работают от UID 10001. Python получает только свой токен, без ключей модели, банка и почты в окружении.

## Проверки разработки

Нужны Node.js 24 и pnpm 11.25.0. Зависимости закреплены в lock-файле.

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm test
pnpm test:integration
docker build --target test -t criterion:tests .
docker build -t criterion:docker .
node tests/container-e2e.mjs
```

Интеграционные тесты запускают реальный Next.js с временной SQLite. Письма, банк и модель имитируются; настоящие ключи не читаются. `container-e2e.mjs` создаёт временный контейнер и том, проверяет сайт с настоящим Python при отключённой внешней сети, затем удаляет только эти тестовые ресурсы. Производственный образ не содержит тестовых подмен. Дополнительно: [модуль ПДн и ограничения распознавания](docs/privacy/README.md).

Проверено 20.11.2026: production-сборка, 76 модульных тестов в Linux, 252 интеграционные проверки и 17 тестов Python. Полный контейнер проверен с 1.5 ГБ RAM без внешней сети: 6 защищённых запросов к имитации модели, восстановление ПДн, DOCX, отказ без отправки модели, резервная копия и сохранность после перезапуска. Регистрация и открытие создания договора проверены в браузере. Живые модель, почта, банк и запуск на инфраструктуре Amvera в эти проверки не входили.
