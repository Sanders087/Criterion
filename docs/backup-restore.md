# SQLite — резервная копия, восстановление и проверка хранилища

## Где смотреть

Фактический путь открытой базы показывает событие `database.ready`. Раз в пять минут `storage.health` сообщает размер базы, WAL и свободное место в байтах, доступ процесса к записи и статус копии. Поле `lastSuccessTimestampSeconds` — время последнего успешного резервирования в секундах Unix UTC. Пропущенное числовое поле означает отсутствие измерения. Права процесса отражают момент проверки, запись конкретной транзакции подтверждает `database.operation_completed`.

Поиск по `requestId` связывает запрос с `database.operation_failed`. Поля `operation` и `durationMs` показывают операцию и её длительность. Для `DB_BUSY` проверяйте `busyTimeoutMs` и `busyTimeoutElapsed`. Последний признак показывает достижение бюджета ожидания 5000 мс либо явный код SQLITE_BUSY_TIMEOUT. `DB_LOCKED` означает конфликт блокировки. `DB_FULL` требует проверить свободное место, квоту тома и размер WAL. `DB_READONLY`, `DB_PERMISSION_DENIED` и `DB_IO_ERROR` указывают на разные проблемы записи. При `DB_CORRUPT` сохраните исходный том и проверяйте копию отдельно. `rolledBack` и `rollbackFailed` фиксируют исход транзакции. Код SQLite из драйвера доступен как `sqliteResultCode`. Ошибка SQL внутри транзакции даёт одно событие отказа.

Начальные эксплуатационные ориентиры для стенда — свободно менее 256 МиБ, WAL растёт несколько последовательных замеров и превысил 128 МиБ, возраст последней копии более 26 часов. Их следует уточнить по объёму и темпу изменения данных. Доступ к журналам и метрикам предоставляется операторам проекта.

## Расписание и хранение

Ответственный за данные включает `SQLITE_BACKUP_ENABLED=true` на одном экземпляре. В контейнере помощник запускается при старте и раз в час. Он создаёт копию, если с последнего подтверждённого успеха прошло 24 часа. Ошибки запуска видны по `storage.backup_job_failed`. Периодический сбор показателей и резервирование выполняются независимо от обработчика healthcheck. Перед миграцией можно запустить внеочередную копию из контейнера от пользователя приложения.

```sh
python scripts/backup-db.py
```

Скрипт использует SQLite Online Backup API и включает зафиксированные записи из WAL. Во временной копии проверяются `integrity_check` и `foreign_key_check`. После закрытия SQLite и синхронизации файла на диске готовый снимок атомарно публикуется в `backups/` рядом с базой. Файловая система должна поддерживать жёсткие ссылки в одном каталоге и синхронизацию каталога. В Linux каталог принадлежит пользователю приложения с правами `0700`, новые файлы создаются с `0600`. Успешный запуск удаляет только автоматически именованные копии старше 14 суток. Состояние последней попытки хранится в `backups/status.json`. При ошибке прежнее время успеха сохраняется. [SQLite Online Backup API](https://sqlite.org/backup.html)

Копии содержат пользовательские данные. Владелец стенда настраивает перенос готовых снимков в отдельное закрытое хранилище, шифрование в хранилище и при передаче, ограничение доступа ответственной группе и удаление по утверждённому сроку. Локальная копия на том же диске разделяет с ним риск потери. Автоматический внешний перенос требует согласованного хранилища и учётных данных команды.

## Контрольное восстановление

Проводите проверку ежемесячно и перед изменением схемы. На изолированном узле подготовьте пустой каталог с доступом только для администратора восстановления. Возьмите выбранный готовый снимок из защищённого хранилища. Для примера ниже он смонтирован только для чтения как `/restore-input/snapshot.sqlite`. Проверяемый образ должен поддерживать миграции этого снимка.

```sh
mkdir -m 700 /tmp/criterion-restore-check
python scripts/backup-db.py --restore /restore-input/snapshot.sqlite --to /tmp/criterion-restore-check/criterion.sqlite
DATABASE_PATH=/tmp/criterion-restore-check/criterion.sqlite node scripts/storage-diagnostics.mjs
```

Команда восстановления создаёт новый файл, проверяет целостность и внешние ключи. Она завершается ошибкой при существующем целевом файле или побочных файлах SQLite. Для повторной проверки используйте новый пустой каталог. На стенде запустите приложение с этим `DATABASE_PATH`, изолированными интеграциями, без действующих ключей и с отключённой автоматической сверкой платежей. Проверьте `database.ready`, вход синтетического пользователя и чтение заранее сохранённой тестовой ревизии. В закрытом журнале обслуживания сохраните дату копии, дату восстановления, версию образа и результат.

При восстановлении рабочего сервиса решение о точке восстановления принимает ответственный за данные. Зафиксируйте потерю более поздних изменений и согласуйте окно. Остановите все экземпляры и фоновые обработчики, сохраните прежний том целиком, восстановите выбранную копию на новом томе и проверьте её совместимым образом. Переключение `DATABASE_PATH` или тома и возобновление записи выполняются после проверки. При неуспехе сохранённый прежний том остаётся доступен для возврата. Перенос в production выполняет ответственный разработчик.

## Постоянство и WAL на Amvera

В предоставленном журнале за 25 ноября 2026 года приложение открыло `/data/criterion.sqlite` в режиме `wal` на томе `nfs4`. SQLite описывает WAL для процессов на одном хосте и указывает на несовместимость с сетевой файловой системой. Один активный экземпляр и один узел записи ограничивают риск параллельного доступа. Совместимость NFS и корректность его блокировок требуют отдельного подтверждения у платформы. Для рабочего окружения согласуйте поддерживаемый диск с локальной семантикой либо перенос базы в подходящую СУБД. [Ограничения SQLite WAL](https://sqlite.org/wal.html)

Для проверки постоянства создайте синтетический маркер в тестовом приложении. Пересоздайте тестовый контейнер, повторно подключите тот же том и проверьте маркер и ранее созданную копию. Успешная проверка на локальной машине покрывает сценарий копирования, а результат для Amvera фиксируется отдельно. Флаг `persistenceVerified` сохраняет значение `false` при одном лишь обнаружении монтирования.
