# Проверка состояния Criterion

| Маршрут GET | Доступ | Что проверяет |
| --- | --- | --- |
| `/api/health/live` | Публичный | HTTP-процесс сайта отвечает. Возвращает 200 и `{"status":"ok"}`. |
| `/api/health/ready` | Публичный | Существующая SQLite открывается для чтения, проверяются права записи процесса на файл, каталог и существующие WAL/SHM, список выполненных миграций соответствует сборке, детектор ПДн ответил `ready` на внутренний запрос с авторизацией. При успехе возвращает 200, при отказе 503. |
| `/api/health` | Публичный | Сохранённый маршрут предыдущей версии, выполняет базовый SQL-запрос приложения. |
| `/api/health/integrations` | Служебный | Состояние SQLite, детектора ПДн, платёжного шлюза, API банка, Resend и модели. |

В Docker проверка запускается автоматически. Для Kubernetes-проб Amvera примените [конфигурацию проекта](../deploy/amvera/probes.yml) через панель платформы. Readiness объединяет одновременные запросы, ждёт ответ детектора до одной секунды и использует результат две секунды. Состояние внешних поставщиков не участвует в решении о перезапуске сайта. База открывается для чтения. Завершение миграций проверяется по именам файлов текущей сборки и записям SQLite. Контрольные суммы проверяет процедура запуска.

## Закрытая проверка

Задайте `MONITORING_TOKEN` в секретах приложения и клиента мониторинга. Используйте отдельное случайное значение длиной 32–256 печатных ASCII-символов без пробелов. Клиент отправляет его в заголовке `Authorization: Bearer <токен>`. При отсутствующем или неверном значении маршрут возвращает 401. Пример для терминала с переменными окружения `CRITERION_ORIGIN` и `MONITORING_TOKEN`:

```sh
curl --silent --show-error --fail \
  --header "Authorization: Bearer ${MONITORING_TOKEN}" \
  "${CRITERION_ORIGIN}/api/health/integrations"
```

В ответе объект `components` содержит `sqlite`, `piiDetector`, `paymentGateway`, `bank`, `resend` и `ai`. Маршрут принимает служебный токен только через заголовок. Личный кабинет, cookie пользователя и токен детектора не дают доступ.

| Поле | Как интерпретировать |
| --- | --- |
| `configured` | Наличие настроек для соответствующего компонента. Для платёжного пути проверяются настройки действующего сценария оплаты, включая тип чека. |
| `reachable` | Получен ответ компонента. HTTP-ошибка может подтверждать доступность адреса. |
| `functional` | Результат последней проверенной операции. Для SQLite это чтение и проверка записей миграций, для ПДн — обработка запроса с корректной структурой ответа, для модели — результат валидации структурированного ответа. Для Resend подтверждением служит принятие сообщения провайдером. |
| `lastCheckedAt` | Время проверки в UTC. Для компонента без наблюдений — `null`. |

Для банка, шлюза, Resend и модели используются события штатных операций этого экземпляра. Чтение health не создаёт заказов, не отправляет писем и не вызывает модель. При неопределённом результате или отсутствии подтверждения соответствующее поле имеет значение `"unknown"`. Через пять минут внешние наблюдения устаревают. Время предыдущего наблюдения остаётся в ответе. После перезапуска кэш экземпляра заполняется заново. Ошибка только на участке связи со шлюзом оставляет прежнее состояние банка до истечения его срока.

У детектора закрытая страница сочетает быструю проверку готовности и последнее наблюдение фактического распознавания. Если проверка готовности успешна, а распознавания после запуска ещё не было, возвращается `reachable: true`, `functional: "unknown"`. Поле `lastFunctionalCheckAt` отдельно показывает возраст подтверждения распознавания, а при провале текущей пробы — время обнаружения отказа. Состояние внешних зависимостей фиксируется и при уровне журнала `error`.
