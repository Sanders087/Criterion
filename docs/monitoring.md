# Мониторинг Criterion

## Подключение тестового стенда

1. Задайте закрытый случайный `MONITORING_TOKEN` в окружении сайта. Для совместимости используйте 64 шестнадцатеричных символа, полученных генератором случайных байтов. Передайте тот же секрет сборщику как файл с правами чтения только для его пользователя.
2. С отдельной машины мониторинга проверьте по HTTPS `/api/health/live`, `/api/health/ready`. Первый отвечает за процесс, второй проверяет обязательные внутренние зависимости. Существующий путь Amvera `/api/health` сохранён.
3. Закрытые маршруты `/api/health/integrations` и `/api/metrics` принимают заголовок `Authorization: Bearer …`. В панели Amvera или прокси ограничьте доступ сетью мониторинга, если доступна такая настройка. Разделяйте секреты сайта, сборщика и детектора. Параметр в URL попадает в историю и журналы прокси.
4. Скопируйте `deploy/monitoring/prometheus.example.yml` и `alerts.yml` в каталог конфигурации Prometheus. Укажите адрес своего тестового стенда и путь к файлу секрета. Проверьте конфигурацию командой `promtool check config prometheus.yml` и правила командой `promtool check rules alerts.yml`. После загрузки у цели `criterion` должен появиться `up == 1`.
5. Для доставки уведомлений укажите согласованный Alertmanager в конфигурации Prometheus, получателя дежурной команды в Alertmanager и проверьте доставку одним тестовым оповещением. Эти файлы можно проверить до подключения общей инфраструктуры. Ответственные за сервис утверждают получателей и пороги после измерения обычной нагрузки.

## Показатели

Счётчики и гистограммы подсчитываются в процессе Next.js до фильтрации уровня логирования. Перезапуск обнуляет их. Для нескольких экземпляров собирайте каждый экземпляр напрямую. Для запросов применяйте `rate` или `increase`. Мгновенные состояния одной базы по репликам агрегируйте через `max`. Закрытый endpoint на 15 секунд кеширует чтение файловой системы и агрегатов SQLite. Неизвестное показание выводится как `NaN`. У счётчиков с метками серия появляется при первом событии.

| Имя | Что измеряет |
| --- | --- |
| `http_requests_total`, `http_request_duration_seconds` | Количество по шаблону маршрута и статусу, распределение длительности по маршруту |
| `application_errors_total` | Ошибки серверных запросов и ошибки отдельно завершённых внутренних операций |
| `payment_gateway_requests_total`, `payment_gateway_timeouts_total` | Исходы и таймауты банковского транспорта со стороны сайта по методу. Метка `component` различает путь через шлюз и прямой вызов банка |
| `payment_unresolved_orders`, `payment_confirmed_without_access` | Заказы, требующие сверки, и существующие договоры, у которых есть подтверждённый платёж без действующего доступа. Штатно удалённый после оплаты договор исключён |
| `payment_notification_processing_seconds` | Время обработки уведомления после его приёма сайтом. Для измерения времени в пути требуется достоверное время отправки банком |
| `mail_send_total` | Принято Resend, отклонено или результат неизвестен. Показатели фактической доставки требуют подтверждённых событий провайдера |
| `pii_failures_total`, `ai_requests_total` | Код и этап сбоя обезличивания, исход запроса к ИИ |
| `sqlite_busy_total`, `sqlite_available`, `sqlite_wal_size_bytes`, `sqlite_database_size_bytes` | Блокировки, возможность получения агрегатов, размеры файлов WAL и БД |
| `storage_free_bytes`, `storage_writable` | Доступное место и права процесса в каталоге БД |
| `backup_last_success_timestamp_seconds`, `backup_last_run_failed` | Время последней проверенной копии и исход последнего запуска |

Для p95 по маршруту используйте `histogram_quantile(0.95, sum by (le,route) (rate(http_request_duration_seconds_bucket[5m])))`. Для p50 и p99 замените первый аргумент на 0.50 и 0.99. Частота уведомлений, количество попыток и задержки рассчитаны по наблюдаемым событиям. [Гистограммы Prometheus](https://prometheus.io/docs/practices/histograms/)

## Оповещения

Файл правил содержит стартовые пороги для 5xx, таймаутов банка, оплаты без доступа, недоступности SQLite и сборщика, места на диске, размера WAL, сбоев почты, ПДн, ИИ и резервного копирования. Единичные ожидаемые отказы пользователя не вызывают оповещение. Состояние OOM и перезапуски процесса проверяются по событиям хостинга. Когда процесс завершился, он уже не может записать собственную метрику причины остановки. [Правила оповещений Prometheus](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)

## Журналы и доступ

Сайт, Python и платёжный шлюз пишут в stdout/stderr своих сервисов. Журналы сайта видны в Amvera, журналы отдельного шлюза — в его systemd journal. Поиск по `requestId`, `operationId` и времени UTC описан в [диагностике](diagnostics.md). Для общего хранилища экспортируйте структурированные события `Criterion diagnostics v2` из этих источников и фильтруйте технические поля до отправки. Идентификаторы операции хранятся в теле записи. Высококардинальные метки делают поиск дорогим.

Для подключения внешнего хранилища предложены срок 14 дней и предел 1 ГиБ на сервис. Настройте удаление по сроку и ротацию по объёму на стороне приёмника. При переполнении ограниченной очереди экспортёра теряются старые записи. Обслуживание запросов продолжается. Лимиты и доступность экспорта журналов Amvera уточняет администратор проекта. Доступ к техническим записям нужен дежурному разработчику и администратору сервиса. Записывайте выдачу и отзыв доступа. При запросе на удаление проверьте все места экспорта и журналы доступа.

В обычном режиме используйте `LOG_LEVEL=info`. Для разбора одного инцидента задайте `LOG_LEVEL=debug` и `LOG_DEBUG_UNTIL` как абсолютное время UTC в пределах следующего часа. После срока приложение фильтрует подробные события на уровне info. Допустимые поля и фильтрация данных одинаковы при любом уровне.
