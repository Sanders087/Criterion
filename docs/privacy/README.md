# Модуль ПДн

Запуск сайта и Python в одном контейнере описан в [основной инструкции](../../README.md). Ветка `docker` содержит полный перенос Criterion 1.15 на Next.js/Node.js и SQLite. Ветка `pdn` сохраняет модуль для исходной версии сайта.

Перед каждым обращением к модели сервер передаёт текст локальному Python-распознавателю (Natasha + Presidio + правила). TypeScript заменяет чувствительные фрагменты случайными маркерами, отправляет защищённый запрос и восстанавливает значения в ответе. Таблица замен живёт в памяти одного запроса. Проверяются также шаблоны, материалы, история и повторный проход ревью. При отказе распознавателя или повреждённых маркерах операция завершается ошибкой; исходный документ сохраняется.

Распознаватель слушает только `127.0.0.1:8100`, проверяет `PII_ANALYZER_TOKEN` и не публикуется наружу. Порт сайта — `3000`. `scripts/run-with-pii.mjs` сначала ждёт Python, затем запускает сайт; при завершении любого процесса останавливает оба. Исходные договоры, таблицы замен и секреты не журналируются.

## Как проверить

`node tests/container-e2e.mjs` после сборки образа `criterion:docker` проверяет реальный сайт, SQLite и Python без внешней сети. Имитируемая модель проверяет отсутствие размеченных ПДн в исходящих запросах. Проверяются интервью, генерация с ревью, правка, экспорт, точное восстановление, отказ распознавателя без отправки модели и сохранность документа после перезапуска.

Отдельные проверки распознавателя из корня репозитория:

```sh
docker build --target test -f services/pii/Dockerfile -t criterion-pii:test .
docker build -f services/pii/Dockerfile -t criterion-pii:staging .
python scripts/test-pii-docker.py --image criterion-pii:staging
node --experimental-strip-types tests/privacy-e2e.mjs --docker
```

Модульные тесты маскирования входят в `pnpm test`. Корпус и разметка — `tests/fixtures/pii-corpus.jsonl`; пример обслуживания офиса — `pii-office-services-case.json`. В тестах нет реальных ключей и обращений к модели.

Корректный текст в браузере подтверждает восстановление, но сам по себе не доказывает, что ПДн не ушли к модели: это проверяется на стороне исходящего запроса в автоматических тестах. Не включать журналирование реальных текстов для такой проверки.

## Известные границы

В синтетическом корпусе найдены все 818 размеченных чувствительных фрагментов, но полностью проходят 315 из 340 примеров: остаются ложные срабатывания и замены лишнего текста. Восстановление проходит 340/340. Это не независимая оценка на реальных договорах и не гарантия отсутствия пропусков в произвольном тексте. Переезд в Docker не меняет алгоритм распознавания. Доступ к живой модели, доставку почты и оплату проверяют отдельно после настройки окружения.


## Диагностика обработки договора

Найдите `requestId` из ответа и `operationId` той же операции. События `pii.stage_completed` и `pii.stage_failed` показывают этап, время, диапазон длины текста и, после проверки ответа детектора, профиль и число возвращённых разметок. Профиль `ru-contract-v1` описывает протокол детектора. Успешная проверка формата разметки сама по себе не измеряет полноту распознавания.

`ai.request_started` и его исход (`ai.request_completed` или `ai.request_failed`) относятся к одному обращению к модели. `ai.response_validated` и `ai.response_validation_failed` относятся к локальной проверке. Для шаблонного договора отдельно проверяются состав и порядок разделов. Один договор может потребовать основного вызова и повторной проверки моделью. При ошибке восстановления ищите `PII_RESTORE_FAILED`, затем `AI_PII_RESTORE_FAILED`. При ошибке сохранения ищите `document.revision_save_failed`; обращения к модели до этого могли завершиться успешно. Успех сохранения подтверждается `document.revision_saved`.

Идентификатор запроса провайдера сохраняется только в формате `req_` и 32 шестнадцатеричных символа. Название модели попадает в логи только при совпадении с разрешённым списком. Эти ограничения не влияют на выбор модели для запроса. Для диагностики не нужны текст договора, список замен или ответ модели.
