# Criterion: модуль ПДн и запуск в Amvera

Схема: **одно приложение, один контейнер, сайт на Node.js + Python**. Сайт обращается к распознавателю по `http://127.0.0.1:8100/analyze`. Наружу открыт только порт сайта `3000`. Перед обращением к модели TypeScript заменяет найденные ПДн маркерами, после ответа восстанавливает значения. Если распознаватель недоступен, запрос к модели блокируется.

**Статус:** ветка `pdn` основана на `release/v1.15`. Модуль ПДн готов к интеграции. Сам сайт в этом checkout ещё использует Workers/D1: перенести его сервер и базу должна команда. Поэтому подключение этой ветки к Amvera сейчас не даст работающий сайт. Шаблоны лежат в `deploy/amvera/`; их нужно включить в сборку перенесённой версии. Отдельное приложение ПДн создавать не требуется.

## 1. Один раз подготовить общую сборку — команда сайта

1. Сохранить `lib/criterion/privacy.ts`, `privacy-detector.ts` и подключение в `ai.ts`. Передавать серверные переменные из `process.env` в `runtime` функций ИИ. Не обходить защищённый путь прямыми запросами к модели.
2. Подготовить production-сборку Node.js с зависимостями, точкой входа и сохранением базы при перезапуске. Текущий `pnpm start` запускает Wrangler и для этого не подходит.
3. Использовать `deploy/amvera/Dockerfile.example`: добавить перед ним собственную стадию `site-build`, которая собирает самодостаточный сервер в `/app/runtime/`. Пример ожидает `server.js`; при другой точке входа изменить `CMD`. Все стадии — Debian bookworm, одна архитектура. Итоговый файл сохранить как корневой `Dockerfile`.
4. Скопировать `deploy/amvera/dockerignore.example` в корневой `.dockerignore`: он исключает локальные секреты, базы, зависимости и кэши. Исходники и зависимости сайта должны собираться внутри Docker. Если команде нужны дополнительные системные библиотеки, добавить их в конечный образ.
5. Скопировать `deploy/amvera/amvera.yml` в корень репозитория. Зафиксировать общую сборку в Git. Настроить миграции и постоянное хранение базы средствами перенесённого сайта.

Пример Dockerfile включает Python 3.12 с закреплёнными зависимостями и запускает оба процесса через `scripts/run-with-pii.mjs`. Скрипт:

- проверяет настройки до запуска;
- запускает Python только на `127.0.0.1:8100`, без ключей модели, базы, банка и почты в его окружении;
- ждёт готовности Python, затем запускает сервер сайта;
- задаёт сайту `HOSTNAME/HOST=0.0.0.0`, `PORT=3000` и локальный `PII_ANALYZER_URL`;
- завершает контейнер при выходе любого процесса и останавливает оба при SIGTERM;
- проверяет готовность обоих процессов командой `node scripts/run-with-pii.mjs --healthcheck`.

Сайт должен действительно читать эти настройки и слушать заданный порт. Не использовать здесь dev-сервер или локальный Miniflare. Python работает без внешней сети для распознавания и без отдельной базы. Таблица замен остаётся в памяти запроса сайта.

## 2. Настроить приложение Amvera

Во вкладке «Репозиторий» связать GitHub `Sanders087/Criterion` с **веткой, где уже объединены перенос сайта и модуль ПДн**. Сейчас `pdn` — ветка модуля для такого объединения. После настройки push запускает сборку; уже существующие изменения можно получить кнопкой «Пулл». Доступ GitHub настраивается в Amvera, токены в исходники не добавляются. [Подключение GitHub](https://docs.amvera.ru/applications/git/webhooks.html).

В разделе «Переменные» достаточно добавить настройки самого сайта и один дополнительный секрет модуля:

| Переменная | Значение |
|---|---|
| `PII_ANALYZER_TOKEN` | Секрет: случайные 32–256 печатных ASCII-символов без пробелов; оба процесса получают его автоматически |
| `OPENAI_API_KEY` | Серверный ключ модели |
| `OPENAI_MODEL` | Модель, согласованная для сайта; текущая интеграция использует `gpt-4.1` по умолчанию |
| `AUTH_PUBLIC_URL` | HTTPS-домен сайта |
| Настройки базы, почты и платежей | По инструкции команды переноса |

`PII_ANALYZER_URL` задаёт стартовый скрипт, вручную заполнять его не нужно. `PORT=3000` указан в Dockerfile. При изменении порта согласованно обновить `amvera.yml` и проверки. Не задавать внешний адрес распознавателя и не открывать порт `8100`.

Подключить HTTPS-домен сайта. В форму Kubernetes-проб Amvera вставить `deploy/amvera/probes.yml`: запуск и готовность проверяют оба процесса, liveness проверяет порт сайта. Пробы — отдельная настройка интерфейса, они не подключаются автоматически из Git. По умолчанию проверяется HTTP-ответ сайта на `/`; для отдельного маршрута готовности можно задать `SITE_HEALTH_PATH=/health` после его реализации. Такая проверка сама по себе не проверяет базу и внешние API. [Пробы Amvera](https://docs.amvera.ru/general/k8sprobe.html).

После изменения переменных перезапустить контейнер. Память и CPU подобрать по совместной нагрузке сайта и распознавателя; измерение отдельного Python-процесса не является оценкой всего приложения.

## 3. Проверить после запуска

В терминале контейнера из `/app`:

```sh
node scripts/run-with-pii.mjs --healthcheck
python scripts/check-pii-endpoint.py --url http://127.0.0.1:8100/analyze
```

Первая команда возвращает код 0. Вторая выводит `ok: true`, `unauthorizedStatus: 401`, `authorizedStatus: 200`. Секрет берётся из окружения и не печатается.

В браузере войти и отправить вымышленный пример из `tests/fixtures/pii-services-contract.txt`. Проверить интервью, создание черновика, сохранение после перезагрузки и экспорт с восстановленными реквизитами. В готовом тексте не должно остаться `CRITERION_PII`.

Корректный текст в браузере не доказывает маскировку до отправки. Автоматическая проверка серверного пути использует настоящий распознаватель и имитацию модели: убеждается, что исходные реквизиты не уходят в запросы интервью, генерации, правок и проверки, и что отказ распознавателя блокирует вызов модели. Не включать журналирование исходных договоров, таблиц замен и секретов.

## Проверки перед объединением

Из корня репозитория, с установленными зависимостями Node.js и работающим Docker:

```sh
node --experimental-strip-types --test tests/*.test.ts tests/run-with-pii.test.mjs services/tbank-gateway/server.test.mjs
node node_modules/typescript/bin/tsc --noEmit --incremental false
docker build --target test -f services/pii/Dockerfile -t criterion-pii:test .
docker build --target runtime -f services/pii/Dockerfile -t criterion-pii:staging .
python scripts/test-pii-docker.py --image criterion-pii:staging
node --experimental-strip-types tests/privacy-e2e.mjs --docker
```

Затем собрать сайт его штатной командой и выполнить `node tests/integration.mjs`, `node tests/auth-integration.mjs`, `node tests/email-integration.mjs`, `node tests/payments-integration.mjs`. В текущем checkout это тесты Workers/D1; при переносе команда адаптирует их к новому серверу и базе. Они используют изолированные данные и имитацию внешних сервисов.

Повторная проверка 17.11.2026: TypeScript и сборка сайта, 68 прикладных тестов Node.js, 4 проверки общего запуска в Linux, 17 тестов Python и 252 серверные проверки прошли. Образ ПДн проверен без сети; пример общего образа проверен с настоящим распознавателем и тестовым Node-сервером, включая изоляцию секретов и SIGTERM. Перенесённый сайт и инфраструктура Amvera в этой проверке не участвовали.

У распознавателя известны ложные срабатывания: в синтетическом корпусе найдены все 818 размеченных чувствительных фрагментов, но полностью проходят 315 из 340 примеров; в части случаев маскируется лишний текст. Восстановление исходного текста проходит 340/340. Это не независимая оценка качества на реальных договорах. Живую модель и полный совместный запуск в Amvera нужно проверить отдельно после переноса сайта.

Справка: [Docker в Amvera](https://docs.amvera.ru/applications/configuration/docker.html), [порты](https://docs.amvera.ru/applications/configuration/network.html), [переменные и секреты](https://docs.amvera.ru/applications/configuration/variables.html).
