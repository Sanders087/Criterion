# Разбор обращения к платёжной системе

При оформлении оплаты сайт резервирует один активный заказ для договора. Запрос `Init` идёт напрямую в банк или через настроенный шлюз. Внутреннее поле `operationId` формируется из UUID сохранённого заказа и позволяет найти запросы, относящиеся к тому же заказу после перезапуска. У каждого обращения к сайту есть отдельный `requestId`. Идентификатор заказа имеет высокую кардинальность и подходит для закрытого журнала, а не для группировки метрик.

## Как меняется заказ

Браузер отправляет `POST /api/payments/checkout`. Сайт проверяет владельца и фиксирует один активный заказ в SQLite. Сумму и подпись формирует сервер. Пользователь получает проверенную ссылку банка либо действие «Проверить оплату». После посещения платёжной страницы банк направляет подписанное уведомление на `POST /api/payments/tbank/notification`, напрямую или через настроенное live-реле. Переход браузера по ссылке возврата запускает проверку через сайт. Основание для выдачи доступа — проверенный ответ API банка или корректное банковское уведомление.

| Предыдущее состояние | Принятое событие | Последствие для заказа и договора |
| --- | --- | --- |
| Активного заказа нет | Создание на сервере → `INITIALIZING` | SQLite резервирует договор до получения результата `Init`. |
| `INITIALIZING` | Успешный `Init`, обычно `NEW` | Сохраняются банковский ID и проверенная ссылка при всё ещё активном заказе. Последовательность уведомлений может опередить ответ `Init`. |
| `INITIALIZING` | Проверенный окончательный отказ → `INIT_FAILED` | Резервирование освобождается. Позднее отдельное действие пользователя может создать новый заказ. |
| `INITIALIZING` | Ответ потерян, противоречив либо срок запроса истёк → `INIT_OUTCOME_UNKNOWN` | Сохраняется исходный заказ. После перезапуска просроченный `INITIALIZING` переводится в это состояние при сверке. |
| `INIT_OUTCOME_UNKNOWN` | `CheckOrder` и `GetState` подтверждают состояние либо повторно подтверждается отсутствие заказа | Найденный платёж обрабатывается по его состоянию. Для отсутствующего заказа применяются условия 335 ниже. |
| Заказ в обработке | `NEW`, `FORM_SHOWED`, `PREAUTHORIZING`, `AUTHORIZING`, `3DS_CHECKING`, `3DS_CHECKED`, `AUTH_FAIL`, `AUTHORIZED`, `CONFIRMING` | Это порядок внутренних рангов. Банк может пропускать промежуточные уведомления. Состояние `AUTH_FAIL` само по себе сохраняет резервирование. `AUTHORIZED` ещё не даёт доступ. |
| Неоплаченный заказ | `CONFIRMED` с подтверждённой суммой, терминалом, банковским ID и успешным кодом | В одной транзакции фиксируются событие и статус, договор получает `billing_state=paid`. При ошибке выдачи изменения откатываются. |
| Неоплаченный заказ | `REJECTED`, `CANCELED`, `DEADLINE_EXPIRED`, `REVERSED` | Банк закрыл заказ. Резервирование снимается. Переход к иному статусу после этой группы отклоняется как устаревший. |
| `CONFIRMED` или более ранний допустимый статус | `PARTIAL_REFUNDED` | Частичный возврат сохраняется в истории, доступ остаётся платным и открытым. Пропущенное уведомление `CONFIRMED` допустимо при проверенном частичном возврате. |
| `CONFIRMED`, `PARTIAL_REFUNDED` или более ранний допустимый статус | `REFUNDED` | Полный возврат переводит существующий договор из `unpaid`/`paid` в `refunded` и закрывает доступ. Новая оплата этого договора в интерфейсе заблокирована. |
| Обработанный заказ | Дубль, запоздалое состояние более низкого ранга или отказ после подтверждения | Дубль подтверждения не даёт второй доступ. Подтверждённый платёж сохраняется при запоздалом отказе, полный возврат сохраняется при запоздалом `CONFIRMED`. |

После штатного удаления оплаченного договора заказ и финансовые события сохраняются. Повторное подтверждение обрабатывается по ранее зафиксированному событию, договор заново не создаётся. Если на первичном подтверждении отсутствует документ для выдачи доступа, обработчик возвращает ошибку и откатывает транзакцию.

## Как читать время и результат

Найдите `payment.transport_started` и соответствующее `payment.transport_completed` либо `payment.transport_failed`. Поля `component`, `bankMethod` и `stage` позволяют отличить запрос сайта от обращения шлюза к банку. При наличии отдельного шлюза сопоставьте обе записи. HTTP 200 транспорта может сопровождаться бизнес-отказом `BANK_REQUEST_REJECTED`.

| Участок | Исходный бюджет | Бюджет P0 |
| --- | --- | --- |
| Сайт → шлюз или напрямую банк | 15 с на каждый вызов | До 15 с, с общим остатком между последовательными вызовами checkout/status |
| Шлюз → банк | 12 с целиком | До 12 с на полный запрос, включая до 3 с на новое соединение |
| Шлюз → сайт при пересылке уведомления | 8 с | 8 с |
| Resend / детектор ПДн / модель | 12 / 8 / 80 с | 12 / 8 / 80 с |

Таймер соединения входит в общий срок. Суммарный срок платёжного транспорта ограничивает обращения к банку, но не задаёт предел на ожидание SQLite или на приём всего клиентского запроса. У старого заказа восстановление может потребовать `CheckOrder`, `GetState`, иногда `Cancel` и повторный `GetState`. Исчерпание бюджета оставляет дальнейшую сверку следующей проверке. На стенде сопоставьте бюджет с таймаутами внешнего прокси и измеренными задержками до банка.

На отдельном шлюзе могут присутствовать `dnsDurationMs`, `tcpDurationMs`, `tlsDurationMs`, семейство адреса, `ttfbMs` до получения заголовков и `responseReadDurationMs`. На уже открытом соединении полезны `connectionReused`, TTFB и время чтения. Отсутствующие измерения пропускаются. Логирование не требует изменения DNS, корневых сертификатов или порядка IPv4/IPv6.

## Как разбирать неизвестный результат

Во время `Init` заказ имеет статус `INITIALIZING`. При неоднозначном ответе, таймауте или обрыве он переходит в `INIT_OUTCOME_UNKNOWN` и сохраняет резервирование. Используйте действие «Проверить оплату». Оно сверяет тот же заказ. Выдача доступа привязана к сохранённому состоянию, а обработка проверенного банковского уведомления и изменение доступа выполняются одной транзакцией. Позднее уведомление с меньшим рангом состояния не отменяет уже обработанный возврат. Повторять `Init` вручную, снимать резервирование SQL-командой или вручную присваивать оплате `CONFIRMED` опасно двойной оплатой или неверной выдачей доступа.

Сайт и шлюз обновляются независимо. Действующая подпись платёжного запроса сохранена. Дополнительная подпись связывает обе метки трассировки с этим запросом. При сочетании старой и новой версий платёжный протокол продолжает работать, но часть журналов придётся искать по времени. Для шлюза используются поставляемые unit-файлы systemd и комплект модулей из инструкции в `services/tbank-gateway/README.md`. В базовом live-реле адрес назначения уведомлений привязан к прежнему сайту Sites. Маршрут реальных уведомлений для Amvera требуется отдельно подтвердить с ответственным за интеграцию.

## События и сверка P1

Проверенный отказ проверки параметра RedirectDueDate (12) или данных запроса (64) освобождает заказ, если в ответе нет признаков созданного платежа. Дублирование OrderId (20), внутренняя ошибка, неполный ответ или иной нераспознанный отказ приводят к проверке существующего заказа. Эти решения основаны на [описании кодов Т-Банка](https://developer.tbank.ru/eacq/intro/errors/error-codes). Указывать новый код как окончательный отказ можно после проверки значения именно для Init.

После потери ответа найдите `payment.init_outcome_unknown` и затем `payment.status_checked` с тем же operationId. Два ответа CheckOrder с кодом 335 должны быть получены после двухминутного периода ожидания, с интервалом от 30 секунд. Проверка состояния закрывает отсутствующий заказ; следующую оплату инициирует пользователь. Потерянную ссылку для платежа NEW можно отменить один раз. Время отправки Cancel сохраняется перед сетевым запросом. Если процесс завершился между записью и отправкой либо ответ потерян, последующие запросы проверяют GetState. Если платёж остаётся NEW, оператор сверяет его с банком перед ручным решением.

Корректные уведомления видны по `payment.notification_received`. Дубли помечаются `payment.notification_duplicate`, причины отказов указывает `payment.notification_rejected.reason`. Изменение состояния и выдача доступа выполняются в одной транзакции. При `payment.access_grant_failed` транзакция откатывается, сервер отвечает ошибкой и последующее проверенное уведомление может повторить выдачу. `payment.access_granted` фиксируется после commit.

## Фоновая сверка

После миграции `0005_payment_reconciliation` фоновую проверку можно включить в окружении запуска сайта. По умолчанию она выключена. Для тестового терминала установите `PAYMENT_RECONCILIATION_ENABLED=true` и перезапустите сайт. `PAYMENT_RECONCILIATION_INTERVAL_SECONDS` задаёт интервал циклов от 10 до 3600 секунд (по умолчанию 60). `PAYMENT_RECONCILIATION_BATCH_SIZE` задаёт число заказов за цикл от 1 до 50 (по умолчанию 20). При некорректном лимите сайт записывает `payment.reconciliation_failed` и продолжает обслуживать пользователей. Значения следует согласовать с лимитами своего терминала.

Воркер проверяет активные заказы, состояние которых не менялось две минуты, подтверждённые оплаты без доступа и ошибки обработки проверенных уведомлений. Он вызывает `CheckOrder` и `GetState`. Доступ выдаётся через ту же транзакцию, что и в обработчике уведомлений. Между заказами есть пауза от одной секунды. Экземпляры, использующие одну базу SQLite с работающими блокировками, разделяют блокировку цикла и отдельную блокировку заказа с ручной проверкой. Срок блокировки заказа 60 секунд при сетевом бюджете 15 секунд. Возможность совместного использования самого хранилища несколькими узлами должна быть подтверждена платформой.

Номер попытки и время следующей проверки записываются перед сетевым вызовом. Неизменившийся заказ получает до шести фоновых попыток с экспоненциальной задержкой, ограниченной часом. Действительно новый банковский статус или первая ошибка подтверждённого уведомления открывают новый бюджет проверки. Дубли одного и того же события бюджет не обновляют. Событие `payment.reconciliation_result` содержит `operationId`, номер попытки и один из результатов `resolved`, `pending`, `failed`, `manual_review`.

При `manual_review` выполните в контейнере приложения `node scripts/payment-reconciliation-review.mjs`. Существующая `DATABASE_PATH` должна указывать на целевую БД. Команда открывает SQLite только для чтения и печатает идентификатор операции, число попыток и дату последней проверки для каждого случая. Найдите цепочку по `operationId` в закрытых журналах, сверьте заказ в кабинете терминала, затем используйте штатную «Проверить оплату» с владельцем договора или повторную доставку подтверждённого уведомления со стороны банка. Если подтверждение расходится с локальным статусом, передайте операцию ответственному за платежи. Для остановки фоновой сверки выставьте `PAYMENT_RECONCILIATION_ENABLED=false` и перезапустите сайт. Резервирования и история сохранятся в БД.
